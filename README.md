This project implements the assignment shown in the supplied screenshots. It uses the standard IBM Telco Customer Churn columns, a 70:30 stratified split, `random_state=42`, Decision Trees, a saved preprocessing/model pipeline, and FastAPI.

**Start here:** put your actual customer CSV in `data/telco_churn.csv`, install the dependencies, and run the notebook top to bottom. This download contains complete source code and an unexecuted notebook. Your actual dataset, fitted model, numerical results and sample response are generated/provided when you run it; they are not fabricated in advance.

## 2. Supply the dataset and execute the notebook

1. Copy the **customer records CSV**, not the data dictionary, into `data/`.
2. Rename it to `telco_churn.csv`, or change `DATA_PATH` in the notebook setup cell to its actual path. For a Windows absolute path, use `Path(r"C:\Users\yourname\Downloads\customers.csv")`.
3. Open `notebook/churn_analysis.ipynb` in JupyterLab (or VS Code).
4. Select the **Python (telco-churn)** kernel.
5. Choose **Run → Run All Cells**. In VS Code, choose **Run All**.
6. Resolve any reported data errors, review the findings, and save the notebook with outputs.

Expected raw columns:

```text
customerID, gender, SeniorCitizen, Partner, Dependents, tenure,
PhoneService, MultipleLines, InternetService, OnlineSecurity,
OnlineBackup, DeviceProtection, TechSupport, StreamingTV, StreamingMovies,
Contract, PaperlessBilling, PaymentMethod, MonthlyCharges, TotalCharges, Churn
```

The notebook expects CSV format and the column names above (surrounding header whitespace is trimmed). `Churn` must be Yes/No. Unknown extra columns are excluded. Invalid target values, negative numeric values, unrecognized category values and unresolved repeated customer IDs stop execution with an explanation. Numeric parse failures are reported and become missing; review those records. Exact normalized duplicate rows are removed. At least five members of each class must remain in training for five-fold cross-validation.

To execute and save notebook outputs from a terminal instead of the UI:

```bash
python -m nbconvert --to notebook --execute --inplace --ExecutePreprocessor.kernel_name=telco-churn --ExecutePreprocessor.timeout=1200 notebook/churn_analysis.ipynb
```

Run it once using either the UI or this command. An optional HTML export for easier review is:

```bash
python -m nbconvert --to html notebook/churn_analysis.ipynb --output-dir reports
```

## 3. Start the API

After training, open a terminal at the project root, activate the same environment, and run:

```bash
python -m uvicorn app:app --reload
```

Open [interactive API documentation](http://127.0.0.1:8000/docs). Expand **POST /predict**, select **Try it out**, paste `sample_request.json`, then **Execute**.

Alternatively, with the server running, open a second terminal at the project root and run:

```bash
python test_api.py
```

This prints the actual prediction/probability, saves `sample_response.json`, and verifies that an empty request, negative tenure and invalid contract return HTTP 422.

Using curl on macOS/Linux:

```bash
curl -X POST http://127.0.0.1:8000/predict -H "Content-Type: application/json" --data-binary @sample_request.json
```

On Windows use `curl.exe` instead of `curl`, or use the cross-platform `python test_api.py` command above.

Response fields:

| Field | Meaning |
|---|---|
| `prediction` | `Yes` or `No` from the saved classifier |
| `churn_probability` | Numeric model probability for class Yes, from 0 to 1 |

The sample JSON response is intentionally generated after fitting so its value matches your actual model. Probabilities are not calibrated risk estimates, particularly if the selected tree uses balanced class weights.

### Input handling

- All 19 predictor keys are required. `customerID` is optional and ignored for prediction.
- Use the exact category spelling in the data dictionary/sample. Surrounding whitespace is stripped.
- A predictor may be JSON `null` for missing data; the saved preprocessing handles it. Omitted keys are rejected so accidental incomplete payloads are visible.
- `TotalCharges` also accepts a blank string as missing or a valid numeric string.
- Negative numeric values, malformed numbers, nonfinite numeric values, invalid categories, extra fields (including `Churn`) and missing required keys produce HTTP 422.
- `SeniorCitizen` accepts 0 or 1. Tenure is a nonnegative whole number. Boolean values are rejected in numeric fields.
- The API validates fields, not every possible cross-field business inconsistency. For example, service combinations should still be checked against the source system when building a production service.
- Missing model: API startup fails with an instruction to train first.
- The model is loaded once at startup; requests do not retrain it.

## Modeling choices and assignment coverage

| Requirement | Implementation |
|---|---|
| Structure, types, missing values, duplicates and target analysis | Notebook sections 1–3 and `reports/data_quality.csv` |
| At least five meaningful visualizations and insights | Eight training-data EDA charts in section 4, each followed by a computed business observation |
| At least two engineered features | Fixed tenure bands and active service count, with construction, rationale and missing-data behavior |
| Decision Tree configurations and justification | Four configurations, compared by five-fold training-only CV; select mean validation F2 |
| Accuracy, precision, recall, F1 and confusion matrix | Final held-out test evaluation in section 7 |
| Business interpretation and precision/recall choice | Actual TP/FP/FN/TN interpretation and retention-cost discussion |
| Feature importance and tree interpretation | Top encoded features, plotted tree, and complete tree rules |
| Saved pipeline and REST API | `model/churn_model.pkl`, shared transformer, FastAPI `/predict` |
| Sample request/response and instructions | Supplied request, generated actual response, this README |
| Bonus work | Small hyperparameter search, balanced-weight candidate, majority-class reference, fold variability and overfitting comparison |

No test-set tuning: the outer 30% is evaluated only after model selection. Imputation and one-hot encoding are fitted within each cross-validation fold via the pipeline. The selected pipeline is then fitted on all 70% training rows and saved after evaluation. The test rows are not added to training afterward.

Recall is emphasized because missed churners represent lost intervention opportunities. F2 gives recall more importance while retaining a precision penalty. This assumption should be revisited if outreach costs/capacity suggest a different tradeoff. Selection uses CV F2; all required metrics are still reported. Tree probabilities use the classifier's default decision rule, with ties selecting No.

References: [scikit-learn leakage guidance](https://scikit-learn.org/stable/common_pitfalls.html), [cross-validation guidance](https://scikit-learn.org/stable/modules/cross_validation.html), [FastAPI request-body validation](https://fastapi.tiangolo.com/tutorial/body/).

## Troubleshooting

| Symptom | Fix |
|---|---|
| CSV not found | Put the CSV at `data/telco_churn.csv` or edit `DATA_PATH` |
| Missing many feature columns | Ensure you loaded customer records, not the data dictionary or a different Telco dataset variant |
| `ModuleNotFoundError: preprocessing` | Keep `preprocessing.py` at project root and open the notebook from root or `notebook/`; start the API from root |
| Model missing | Run all notebook cells, including the save section, before starting FastAPI |
| Package import error in notebook | Select the Python (telco-churn) kernel you created |
| HTTP 422 | Read the response detail; compare your payload with `sample_request.json` |
| Port 8000 already in use | Stop the previous server or use `--port 8001`; change the test script URL accordingly |
| Model version mismatch | Use the training environment versions recorded in reports |

The project is designed for the supplied historical assignment dataset. Production use would additionally need a defined prediction horizon, feature-availability checks, temporal validation, campaign evaluation and monitoring.
